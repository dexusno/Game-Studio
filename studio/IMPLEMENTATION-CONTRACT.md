# Studio implementation contract

This file defines the studio's versioned records and tooling interfaces. Keep the CLI, templates, and workflow documentation consistent with it when extending the studio.

- Root: `D:\Game-Studio`, GitHub `dexusno/Game-Studio`, one repository containing studio tooling and `games/<slug>/` for each game.
- Native Codex skills: `.agents/skills/<name>/SKILL.md`, optional `agents/openai.yaml`.
- Native Codex agents: standalone `.codex/agents/<name>.toml`, required `name`, `description`, `developer_instructions`. Inherit the user's model and permissions; no pinned models, no fabricated tool names.
- Skills: `studio-director`, `game-research`, `game-prototype`, `game-production`, `game-release`, `game-retrospective`.
- Agent roles: `producer`, `trend-scout`, `market-analyst`, `game-designer`, `game-engineer`, `art-director`, `audio-designer`, `qa-playtester`, `release-producer`. These are on-demand specializations, not always-running staff.
- Shared role workflow guidance: `studio/WORKFLOW.md`; operating preferences: `studio/CHARTER.md`; agent routing: `studio/TEAM.md`.
- Research: source catalog `research/sources.json`, rubric/method `research/README.md`, dated runs under `research/runs/`, persistent candidates under `research/opportunities/*.json`. Archive by status; do not silently delete ideas.
- Candidate shape: `schema_version: 1`, `id`, `title`, `status` (`draft`, `shortlisted`, `selected`, `held`, `rejected`, `shipped`), `hook`, `audience`, `core_loop`, `trend_stage` (`rising`, `near-peak`, `steady`, `declining`, `unverified`), `confidence` (`low`, `medium`, `high`), `scores` (0..5 each: `demand`, `distinctiveness`, `fun_potential`, `scope_fit`, `distribution`), `evidence` (array of records with `url`, `accessed_on`, `claim`, `kind`: `observed`, `reported`, `estimated`, or `hypothesis`), `risks` (strings), `next_test`, `decision_reason`. Optional additional fields are allowed.
- Score is an aid, not a sales forecast: demand 20%, distinctiveness 20%, fun potential 20%, scope fit 25%, distribution 15%. Trend timing/confidence stay separate. Unverified hypotheses are never described as proven trends. Actual playtesting is required before calling fun validated.
- Game manifest `games/<slug>/game.json`: schema version 1, `slug`, `title`, `engine` (`unreal`, `godot`, `unity`, `web`, `custom`, `undecided`), `platforms` (non-empty array), `stage` (`concept`, `prototype`, `production`, `release-candidate`, `released`, `maintenance`, `parked`), `created_on`, `source_opportunity` (string or null), `budget` (`target_days`, `human_hours`, `cash_usd`; nonnegative numbers), optional additional fields.
- Template at `templates/game/` creates `game.json`, `AGENTS.md`, `README.md`, `BRIEF.md`, `STATUS.md`, `DECISIONS.md`, `BUILD.md`, `QA.md`, `RELEASE.md`, `assets/manifest.csv`, `src/`, `marketing/`. Templates are honest blank plans, not a working engine project.
- CLI: Python 3.11+ standard library `scripts/studio.py`: `new-game SLUG --title TITLE --engine ENGINE [--root ROOT]`; `status [--root ROOT]`; `validate [--root ROOT]`; `score PATH`; `doctor [--root ROOT]`; `steam-snapshot --apps APPID [APPID ...] --out PATH`. Repository location defaults to script parent-parent. Root overridable for isolated tests. `new-game` refuses overwrites and traversal, stages fully before adding a game, leaves no partial project after failure.
- `status` discovers manifests. No second writable portfolio registry. The producer owns the current portfolio report and the assigned game's `STATUS.md`; agents own assigned files; no concurrent writers to the same file.
- `validate` checks real JSON/TOML/frontmatter shapes, references/required template layout, and manifests/candidates. No engine/build pass implied. `doctor` reports optional tools separately from required Python/Git. Actual private machine paths can be recorded in ignored `config.local.json`.
- Steam snapshot: timestamped source URLs, USD list/current prices and consistently filtered all-language Steam-purchase review counts. Not a sales estimator. Explicit failure status; no made-up zero values or silent partial output. No API keys needed.
- Meaningful CLI tests in `tests/`, CI in `.github/workflows/studio-checks.yml`. Test hostile paths, existing content, generated game validation, malformed records, mocked Steam behavior; no network required in CI.
- Keep scripts/documents free of Appdrip secrets and app source. BMAD concepts may inspire original text; track research and decisions in `studio/decisions/` with exact upstream links. No wholesale installer required.
- No game selected by this setup. A small dated research pilot may create candidates as `draft`/`shortlisted`; it must not silently greenlight or implement a game. Existing `D:\Breakout` remains an external learning reference.
