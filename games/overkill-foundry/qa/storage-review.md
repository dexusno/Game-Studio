## SQ-01 — stale revision accepted after backup repair

**Severity: high, data overwrite. Status: corrected by author and independently rechecked.** Affected build: initial hashes above. Affected implementation: `platform/src/windows_save_store.cpp`, initial lines 49 and 61–65; API promise at `platform/include/overkill/save_store.hpp:20`.

Reproduction, executed by independent probe `revision_reuse_after_recovery`:

1. Commit payload A at revision 1, then B at revision 2. Retain B and its revision in a stale client.
2. Damage the primary file. Read recovers backup A at revision 1.
3. Commit repaired state with expected revision 1. It becomes revision 2 again.
4. Commit stale B plus a later purchase using the retained expected revision 2.

Expected: the stale writer is rejected and the repaired state remains intact. Actual: the stale commit succeeds at revision 3 and replaces the repair. The lock serializes current writers but cannot distinguish different states with the same reused revision.

Observed probe output:

```text
FAIL revision_reuse_after_recovery: stale B revision 2 accepted after repair reused revision 2; repaired state overwritten at revision 3
RESULT 12 passed; 1 failed.
```

Evidence: `platform/build/qa-storage/initial-run.log` and `platform/build/qa-storage/artifacts/47732/`. The implementation owner corrected the API to compare a random 128-bit commit identity encoded in `OFSAVE02`, generated by Windows BCryptGenRandom. Revisions may still repeat after recovery; the compare token does not intentionally repeat. Reviewer did not change production code.

Independent recheck on source SHA-256 `CD2086ECD6F398F22D87775F3ADE7F45402C8623BAA82AC13394B4330EE876CC` passes both the original case and the additional case where the repaired payload and revision exactly match the stale client's state. The repaired token differs and the stale write is rejected in both cases. The header also now documents ambiguous failures; `reconcileRequired` is observed true after both injected exceptions and an actual post-replacement Windows sharing error. Recheck log: `platform/build/qa-storage/token-retest-run.log`; artifacts: `platform/build/qa-storage/artifacts/49124/`. Result: **14 passing groups, 1 failing group (SQ-02)**; author CTest remains **1/1 passing**.

## SQ-02 — short incompatible envelope bypasses version refusal

**Severity: medium, unsafe compatibility fallback. Status: corrected by author and independently rechecked.** Affected build: post-SQ-01 source hash `CD2086ECD6F398F22D87775F3ADE7F45402C8623BAA82AC13394B4330EE876CC`. Affected file: `platform/src/windows_save_store.cpp`, `readOne` checked version-2 minimum length before inspecting the envelope marker.

Reproduction, executed by `legacy_short_envelope`:

1. Create a version-2 primary and valid version-2 `.previous`.
2. Put the exact valid 33-byte `OFSAVE01` A/revision-1 envelope from the initial implementation in the primary path. Its fixture bytes are retained in the probe, so reproduction does not depend on earlier generated files.
3. Call `read()`.

Expected: report the unsupported primary format, with no fallback or overwrite absent an explicit migration. Actual: the version-2 64-byte minimum rejects the file as generic corruption before the version check; `read()` returns the backup as a successful recovery. This violates the intended incompatibility barrier, even though this is an unreleased foundation and no real player save loss has been observed.

Evidence: `FAIL legacy_short_envelope: valid 33-byte OFSAVE01 primary silently recovered a v2 backup instead of reporting incompatibility` in `token-retest-run.log` and artifacts directory `49124`. The author moved the format-specific minimum after the version check. Final source hash `5EA6C9B32D8432BB8793E18C5623AC3B987508FB193BF1708346CFBF666E22A7` rejects this exact fixture as incompatible and refuses replacement. Ordinary supported-version truncation still recovers a valid backup. No migration or game-rule change was introduced.

## Passed checks on the initial artifact

The author's actual native suite passed **1/1 CTest targets**, including four child processes ending through `ExitProcess(75)` at the declared boundaries. Prior payload/revision returned after TemporaryWritten/TemporaryFlushed; complete new payload/revision returned after Replaced/CommitFlushed. Initial artifacts: `platform/build/storage-test-artifacts/40432/`. The final rerun and its retained log are listed below.

Independent probe result: **12 groups passed, 1 failed (SQ-01)**. Passed groups establish:

- Ordinary stale revision rejection with no recovery, and unchanged newer payload.
- Byte-for-byte preservation of a valid `.previous` through repair; subsequent primary damage recovers that backup.
- A full envelope marked with an unsupported envelope version is rejected without rolling back or replacing it.
- Changes to revision, length, integrity value, payload and truncation recover the valid backup; two invalid copies reject further commits without overwriting the primary.
- A held exclusive `.lock` blocks commit without modifying the primary; closing the handle permits the next commit despite the lock file remaining.
- A denied temporary open and a primary handle denying replacement fail before replacement, preserve the primary, and allow retry after handle release.
- Thrown exceptions at each of the four boundaries preserve a complete old/new envelope and release the lock.
- Eight additional real child-process exits: first-ever commit and damaged-primary repair at all four boundaries. Reads return no committed save before first-save replacement, otherwise the expected complete old/new state. Repair preserves backup bytes; follow-up commits prove OS locks and abandoned temporary files do not prevent recovery.
- Empty payload and a `2 MiB + 73 byte` binary payload round-trip, exercising multiple ReadFile/WriteFile chunks.

These are storage checks. The payloads such as `credits=...` are opaque synthetic bytes; no campaign transaction, receipt interpreter, purchase, reward, death, or Continue implementation was invoked.

## Ambiguous failure observation

The `post_replacement_flush_failure` probe opens the new primary with a real read handle denying write at `SavePoint::Replaced`. The subsequent flush open fails with Windows error 32. `commit` returns false, while `read` sees the complete new revision and payload. This is expected possible ambiguity after installation, not evidence of a half-written transaction. The corrected header explains reload-and-reconcile semantics and the result flags `reconcileRequired=true`; both were rechecked. A failed return must never be interpreted by campaign integration as proof that an operation did not commit.

## Not run / coverage limits

- Campaign schema/content validation, migration, receipt idempotence, original fight-entry restart, Collection/unlock preservation, reward reopening/abandonment, purchases and all complete P11 flows. Those systems are outside this storage increment.
- Packaged Windows game startup/play/failure/restart/quit, human controls/focus/resolution/performance, audio and graphical/headless parity. No gameplay or visual-quality approval is claimed.
- Abrupt hardware power loss, device write-cache behavior, arbitrary interruption inside a Windows API call, full-disk conditions, network/cloud-synced/FAT/ReFS storage, restricted-user ACL matrix, pathological file sizes and hardware faults. Boundary exits leave the OS running and cannot establish power-loss guarantees.
- Human playtest, enjoyment, readability and visual approval: none. There is no human play session in this evidence.

API behavior was checked against Microsoft's current [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew), [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), and [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) references on 20 September 2026. ReplaceFile's unsupported write-through flag and documented failure states are reasons to keep the evidence limited to observed local tests; these references do not establish game-level durability.
